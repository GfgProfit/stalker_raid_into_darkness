# Measurement contract

## PIX diagnostics in non-Development Release

`-benchmark-pix-diagnostic` is an explicit opt-in only in a requested CleanReleaseRoute07 session. Clean startup still rejects PIX capturer modules. Diagnostic admission permits the exact PIX GPU/timing capturer names while preserving their real `externalDiagnostics` value and native module paths. Known RTSS, FramePacingNative, RenderDoc and Nsight injection modules remain forbidden. Camera, weather, resolution, API, quality and pacing checks remain active. Additional benchmark observers are rejected in this mode.

Diagnostic results use `status=diagnostic-completed`, `measurementClass=pix-diagnostic`, `instrumented=true` and `eligibleForFpsComparison=false`. They are not a clean FPS series, even when no capture was ultimately obtained. A clean comparison must reject these records rather than silently pooling their timestamps. The launcher always writes `mainSeries=false`.

`-benchmark-pix-capture-position 1..4` requests one present-to-present structural capture after 1.5 seconds of that position. It requires external PIX launch before D3D12 device creation. No position is skipped, and no route settings change. `pix-diagnostic.json` distinguishes requested, attached-reported and capture-file state; actual suitability requires opening and inspecting the capture.

`clock-sync.csv` records original route Stopwatch ticks and native QPC brackets, PID/TID, frame, position and marker sequence. Additional Stopwatch reads bracket the native call, bounding clock conversion rather than assuming equal clock epochs. `gpu-frame-markers.csv` records submitted camera identity markers and their native recording-thread QPC. Verify corresponding `RC06CPU`/`RC06GPU` events in the saved capture at multiple times, check monotonic order and bound residual error before using route windows. A CPU Update timestamp is not Present; a GPU camera marker is not an HDRP pass or a guarantee that a simultaneously running CPU frame matches it.

The optional native bridge and its official PIX runtime live entirely under this module. See `CleanReleaseRoute07/Native/README.md` for API contracts and reproducible builds. Instrumentation is bounded, opt-in, and writes CSV only during teardown. Overflow makes the record unsuitable. Live timestamps and structural replay counters must remain separate; export pagination, queue ownership, overlap levels and truncation must be validated before population claims.

The location History work test is a warmed local microbenchmark of a History pass on location data at a fixed Unity frame number. Its compiled delegate calls the production implementation repeatedly. It does not measure inclusive MatrixHistory CPU time in real frames, camera culling, submissions or GPU work. Do not combine it with recorder/native timings.

The previous 212.68 to 52.50 microseconds describe this local fixed-frame pass. Preserve the original evidence and use this scope when quoting it.

`history-work.json` includes a same-thread allocation-counter positive control. It allocates a 65,536-byte managed array between counter reads and keeps the object alive beyond the second read. A counter is usable only if it observes at least the payload size. When `allocationCounter.valid` is false, zero deltas in History and route-overhead samples do not establish zero allocations. Code inspection for explicit allocations is separate evidence.

`-shadow-only-mode A|B` is an external feasibility experiment. A keeps the existing renderer path. B additionally evaluates `XRayShadowInfluence` against offscreen casting candidates using the full camera far plane, without enabling production rejection. Directional sources are placed first as the one cheaper alternative to the original source order; technical runs check that ordering preserves the rejection count. The startup component list does not certify native particle lights, subsequent lifecycle changes or cached-shadow coverage. Every candidate therefore remains submitted. This measures the cost and potential rejection of the rejected prototype; it is not a comparison against an accepted production filter.

`-shadow-only-technical` records candidates, experimental potential rejections, actual renderer counts, fallback, source observations, screenshots and warmed local preparation/check costs separately from the timing series. Standalone candidate gathering duplicates renderer traversal and is reported separately. None of these counts is a GPU shadow-draw measurement. The timing series uses the same prepared matrix path in both modes.


## Prepared submission groups

`-location-batching U|G1` compares the current renderer with GameConfig.InstanceSubmissionGroupingEnabled false or true. The module applies this value to private in-memory configuration copies before warmup and restores the original renderer configuration on completion or Abort. Both modes retain identical source batch sets and prepared plans, matrices, payload, materials, lighting and shared fixes. No production configuration asset is written. Historical LocationBatching03/04 Players used A/B and private sets without plans; those command lines describe retained historical binaries, not the current launcher.

`-batching-counters` installs an external wrapper around the real renderer callback and records its elapsed callback duration plus actual `Graphics.RenderMeshInstanced` call/instance counters. These technical runs are separate from the timing series. The callback scope includes the renderer's preparation and submission work; it excludes subsequent HDRP/native culling, render-thread work and GPU execution. Color instances count source instances selected for color submission, not visible pixels. GPU draw reductions are not inferred from CPU submissions.

The ordinary timing series installs no batching observer or callback wrapper. Each route uses U1/G1_1/G1_2/U2, 8 seconds of warmup on the first pose, four 5-second positions, and no previsit. Full assigns each interval to its left timestamp, including the interval ending at the next boundary. Stable keeps intervals whose left timestamp is at least 0.5 seconds after the position start. FPS is interval count divided by summed elapsed time. Percentiles interpolate at (N-1)*p. 1% low is 1000 divided by the mean of the slowest ceil(0.01*N) frame times, available for at least 100 samples. Report each run and position, both pairs and both windows separately; do not pool different routes.

`-batching-capture` adds overview PNGs to technical runs. Their wind/effect phases are not synchronized, so they are not a pixel-equivalence test. The production Editor tests separately compare an isolated fixed-light shadow fixture with offscreen casters, using original/prepared data and a no-caster positive control.


Production admission is controlled by the shared `GameConfig.InstanceSubmissionGroupingEnabled` setting, which remains false. The current module's U/G1 session overrides do not change this default or ordinary startup. General matrix, history, material-binding and Editor preparation fixes remain active independently. A favorable Player Eye result alone does not admit grouping as the default for other locations.

LocationBatching04 uses three states: U without groups, G0 with the correctness fixes and earlier grouping costs, and G1 with the same correctness fixes plus callback caches. Its single main sequence is U1, G0_1, G1_1, G1_2, G0_2, U2. Separate technical runs report actual calls, instances, color instances, elapsed callback samples and memory scope. Elapsed callback duration includes time inside native calls and is not pure CPU execution time. Retained Player source revisions and build GUIDs identify the measured candidates separately from the later production-default decision.

LocationBatching05 uses one current Release Player, two independently selected scene-bound profiles, and eight main processes in total. Overview preserves its historical 90 degree FOV, 0.1 near and 10000 far plane. Player Eye uses the user world poses and FPS_Player camera settings: StalkerMovementProfile supplies 95 degree FOV and 0.05 near at initialization; the prefab supplies far=1000. Lens differences are part of the recorded route definitions, not a controlled height-only experiment. Settings match within each U/G1 pair.

Technical source color candidates use the same wind-expanded source bounds, distance eligibility and camera frustum. Shadow-only sources remain submitted where casting is enabled; fully excluded source counts are reported separately. Existing renderer counters describe actual submission calls and instance arguments. Existing group scratch is inspected once per pose for active merged groups and mixed-visibility fallback; no new production hook is installed. Callback duration is a Stopwatch-weighted arithmetic mean of observed real Game-camera callback samples over the one-second pose window. Standalone visibility inspection and PNG capture occur outside the wrapped callback and only in technical runs. These measurements do not establish occlusion, visible pixels, GPU draws or exclusive CPU time.
