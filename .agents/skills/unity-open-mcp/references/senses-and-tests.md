# Senses and tests

## Select the evidence before running

1. You MUST verify the absolute project path, installed versions and unsaved scenes, then use the active Production Editor for routine validation. Select the narrowest checks that exercise the affected behavior. Before a change that may affect references, you MUST verify the save and serialization contracts in scope and record relevant asset and `.meta` GUIDs, serialized bindings, assembly boundaries and dependent references. After the change, you MUST compare them and check for missing scripts, broken references and unintended asset changes.
2. For changes requiring Unity validation, you MUST establish the relevant current baseline. Before testing a C# change, you MUST verify that the Editor loaded the current compile. Use [Compile and Safe Mode](compile-and-safe-mode.md) to distinguish completed compile, stale assemblies, errors and unknown outcomes. For Editor-only behavior, you SHOULD prefer relevant EditMode coverage. You MUST use Play Mode for affected scene reload, runtime integration and gameplay. You MUST use a Player build when the change or required check depends on Player behavior, build configuration or performance. Distinguish per-platform, per-scene and per-configuration coverage. Static checks suffice for documentation-only changes.
3. You MUST keep essential regression tests and fixtures in Production, including X-Ray format parsing, importer correctness, material generation, Original TBN, Hemisphere, Flora, MT_LOD, Decals, renderer lifecycle, MO2 resolution and GUID preservation. Relocating essential tests REQUIRES an audit that proves safety and explicit user approval. Moving complete assembly/asset dependency groups for specialized one-time diagnostics REQUIRES dependency evidence and explicit approval.
4. You MUST configure unique Archive paths before producing logs, test results, captures, metrics or builds. You MUST use evidence to distinguish pre-existing failures from regressions. If execution is blocked, you MUST record the exact missing check, available partial evidence, impact and manual validation steps. You MUST report the modified and tested projects, executed tests and results, and absolute evidence paths. For isolated testing, report correspondence with the Production revision, relevant differences and changes that exist only in isolation.
5. Before integrating a successful isolated experiment, you MUST confirm reproducibility and the minimal Production change and obtain any required approval. You MUST preserve GUIDs and serialized references, run the relevant Production regressions and report the Production result. An isolated result does not establish Production integration.

## Agent senses (live-only, no batch fallback)

- `**unity_senses_run_tests`** — EditMode + PlayMode test runner with per-test pass/fail. Filter by assembly / namespace / class / method. Set `include_passes: false` on large suites to avoid truncation. You MUST NOT start a second `run_tests` call before the first resolves (no concurrency guard; results interleave). Results are retrieved by the server polling a results file (NOT via `unity_senses_pull_events`). A run that is superseded by a newer run, or aborted when play mode is entered mid-EditMode-run, writes a terminal file with `status:"aborted"` + `reason` (`superseded_by_run` | `playmode_entered`) — the poll resolves to that instead of timing out.
  - **Zero-match looks like "no results".** When the filter matches zero tests, `TestRunnerApi.Execute` runs nothing and the result is `status:"completed"` with `summary.total:0` and a `note` — that is a no-match filter, not a failure. `test_class` maps to NUnit `groupNames` (a partial/group match), and `assembly_name` must name a real test assembly.
  - **Single-test diagnostic.** For verbatim NUnit assertion failures, a direct method invocation through `unity_open_mcp_invoke_method` may help when the method can run safely in that context. Without the TestRunner lifecycle this does not verify fixtures, setup/teardown, async execution, or Play Mode. Use the normal filtered runner for those checks.
  - **Brief reloading window after a run.** A test run (PlayMode especially) can trigger a Unity domain reload that freezes the bridge's heartbeat for a few seconds. The MCP server recognizes an in-flight run and treats that window as a normal reload rather than a dead bridge, so subsequent tools keep waiting instead of failing fast with `bridge_compile_failed`. For robustness, after `run_tests` returns `{status:"started", runId}`, poll the result file (or call `ping` / `editor_status`) once before issuing other tools — the run itself is async and the bridge may still be settling.
  - **Headless / CI alternative.** `run_tests` has no MCP batch route. For CLI tests in an eligible headless project, you MUST follow the batch skill linked from the entrypoint, including absolute Archive output paths, `-runTests` without `-quit`, and fresh test XML. Known batchmode-only failures that may pass in the live Editor include in-process HTTP-server lifecycle (socket-disposed), GPU/SceneView without a graphics device, Unity 6's removed `LogEntries.GetEntries(List<LogEntry>)` API, MSBuild/Roslyn `Microsoft.Build.Utilities.Core` host load, and TimeManager SerializedProperty float access. Check the failure in the intended environment before concluding it is a regression.
- `**unity_senses_read_console`** — console entries via reflection. Filter `type: "error"` to inspect observed failures. A clean console alone does not prove the current sources compiled. `detail: "summary"` for messages only (saves tokens); `detail: "verbose"` includes Unity-internal frames.
- `**unity_senses_screenshot**` — Scene / Game / **composed** / isolated 2x2 composite of one GameObject. `view: "game"` renders `Camera.main` **only** — Screen-Space Overlay UI and multi-camera compositions are NOT in the frame; use `view: "composed"` to verify UI edits (the full player frame: all cameras by depth + Overlay canvases).
- `**unity_senses_screenshot_camera**` — render from an arbitrary world-space pose (position + rotation + fov) without moving the scene/game camera; transient camera, scene camera untouched.
- `**unity_senses_capture_inline**` — same targets as `screenshot` but returns the PNG as an inline base64 image (no temp file) for agents that don't read the filesystem.
- `**unity_senses_visual_compare**` — visual regression: capture a named reference snapshot (`action: save`) from scene / game / isolated view, then `action: compare` a later capture against it to check whether an edit visually broke anything. Returns `pixelDiffPercent`, `mismatchedPixels`, `perceptualDistance` (8x8 average-hash Hamming distance — tolerates minor anti-aliasing drift), and `match` (true when `pixelDiffPercent <= sensitivity * 100`; default `sensitivity: 0.01` = 1%). On a non-zero diff, returns an inline diff image (mismatched pixels highlighted red over the current frame). References persist under `~/.unity-open-mcp/screenshots/references/` unless the tool supports redirecting them. For this project, you MUST choose Archive-backed captures. If the tool cannot place new references there, use inline capture and save evidence to Archive. `action: list` / `delete` manage the tool’s reference store. You MUST preserve existing references. The `compare` resamples the current capture to the reference dimensions if they differ, so the diff is resolution-stable.
- `**unity_senses_screenshot_window**` — capture an Editor window (Console / Hierarchy / Inspector / Project / Scene / Game / custom). **Windows-only**: on macOS/Linux returns `not_supported` (the editor-window backbuffer is not bound during bridge dispatch, so a readback produces a blank frame) — use the OS screen-capture tool, or `screenshot {view:"composed"}` for the rendered Game view. On Windows, a blank/solid-color frame is rejected with `blank_capture` rather than reported as `ok`.
- `**unity_senses_frame_debugger**` — control Unity's Frame Debugger: `action: enable` opens the window and starts capturing, `action: disable` stops it, `action: list` returns the draw-call list (shader / pass / material / render target / vertex/index/instance counts per call). Read-only (gate off); the response reports `windowOpened` so you know Editor UI may have changed. Enable, render a frame, then call `list` to inspect draw calls. You MUST restore task-owned instrumentation to the prior Editor state when done.
- `**unity_senses_profiler_capture**` / `profiler_memory` / `profiler_rendering` — frame hierarchy, memory allocators, rendering env.
- `**unity_senses_profiler_capture_frame`** — single-frame deep profiler capture. Returns one (or a few, via `frame_count`) frame's full sample tree, optionally filtered by `modules` (Profiler category names, e.g. "CPU,Rendering"). Deeper than `profiler_capture`; bound output with `max_depth` (default 8) and `max_items` (default 200). If the Profiler is off, the tool enables it for the capture, then restores it to disabled once data is captured; `profilerWasEnabled` reports the PRIOR state. On a cold capture (Profiler was off and no frame is recorded yet) the tool returns `status:"warming_up"` instead of blocking — it leaves the Profiler enabled, so re-issue the call shortly to receive the frame data. If abandoning a cold capture, you MUST restore the Profiler to its prior state.
- `**unity_senses_spatial_query**` — physics-based raycast / overlap / bounds / ground_check / nearest against the live scene.
- `**unity_senses_pull_events**` — incremental console logs + editor-state transitions (compile start/stop, play-mode). Cheaper than `read_console` for "what happened since my last call"; first call opens the stream, later calls return only new events. Returns `bridge_unavailable` when the bridge is down. The stream self-heals across Unity restarts and domain reloads (the server re-reads the bridge port+token from the instance lock on every reconnect, backing off 2s→30s), so after a reload keep polling instead of assuming the stream is dead.

**Verification habit.** After any C# change, before reporting success, you MUST inspect error diagnostics or run relevant tests through the verified current compile. You MUST check the terminal result. A stale domain, an aborted run, zero matches, or a clean console alone leaves the affected test coverage unverified.

### Return serialization (execute_csharp / invoke_method)

Results are walked by a depth-limited reflective serializer before becoming `mutation.output`:

- Structs/POCOs → JSON objects with public fields/props (`return new Vector3(1,2,3)` → `{"$type":"Vector3","x":1,"y":2,"z":3}`).
- Lists truncate to 100 items (`max_items` configurable); truncated arrays report `{"items":[...],"truncated":N}`.
- Recursion caps at depth 4 (`max_depth` configurable).
- Cycles / `UnityEngine.Object` refs never infinite-loop — back-edges become `{"$ref":"TypeName"}`, Unity objects become `{"$type":...,"name":...,"instanceId":...}`.
- **Malformed output is rejected, not trusted.** The per-member walk is try/catch'd, but an exception can still escape mid-walk (e.g. a `TypeLoadException` when a field references a missing assembly), leaving unbalanced JSON. `execute_csharp` validates the serialized output before it enters the envelope; if it isn't a balanced JSON object the call fails with `error.code = "execution_error"` and a diagnostic naming the return type. On the rare chance the body is still corrupted in transit, the MCP server surfaces `bridge_response_unparsable` instead of a fake success — either way you'll never see a `_compileVerify`-annotated result missing its `mutation` block.

### `execute_csharp` read-only probe flag (`read_only`)

`execute_csharp` defaults to mutating and REQUIRES a non-empty `paths_hint`. For pure inspection, pass `read_only: true`: no scope, checkpoint, or validation is needed, even when the scene is dirty or a hint was supplied. The caller asserts its own behavior. You MUST NOT use this flag for writes or disruptive lifecycle transitions. Known compile/refresh, scene-switch, and play-transition calls retain protection, and the deny heuristic still applies. See [Batch and gates](batch-and-gates.md) for request and batch guidance.
