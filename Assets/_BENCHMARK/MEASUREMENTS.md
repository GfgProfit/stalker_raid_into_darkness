# Measurement contract

## Startup focus admission

Timing routes wait for 0.5 seconds of observed `Application.isFocused` before starting warmup. An unfocused observation or `OnApplicationFocus(false)` before start resets settling; invalid or regressing startup timestamps restart admission. The existing strict focus violation policy remains active after start. A Win32 foreground window is not substituted for Unity focus. This startup delay is outside the established 8-second warmup and four 5-second positions; their timings are unchanged. Configuration-only checks retain their existing behavior. `result.json` records `startupFocusSettleSeconds`; earlier focus-violated attempts remain invalid evidence and are not relabelled.

`FrameTimingDiagnosticSession` calls only `GetLatestTimings` and `CaptureFrameTimings` during the route. CPU thread/frame durations include elapsed waits and overhead; they are not OS running time. CPU/GPU and nested timings overlap and must not be added into a frame budget. This high-level diagnostic identifies scheduling or CPU/GPU candidates; it does not supply HDRP pass timings. ## OS thread CPU and Release recorder inventory

`-clean-route -benchmark-cpu-diagnostic -location-batching U` requests a separate `release-cpu-diagnostic` session in a normal non-Development build. Frame Timing Stats must be disabled. Native submission A or B may be selected explicitly. PIX, FTM, configuration-only/no-timing routes and other benchmark observers are rejected. The result is instrumented and ineligible for clean FPS comparison; launch metadata must agree. Without the flag the controller creates no CPU session, native thread handle or profiler recorder.

No marker configuration means inventory plus OS thread CPU sampling only. `-benchmark-cpu-marker-config <Archive JSON>` accepts `{"markers":[{"category":"exact inventory category","name":"exact inventory name","unit":"exact inventory unit"}]}` with at most 32 unique selections. Marker availability comes from the running Release Player, not the Editor. `cpu-marker-inventory.csv` records names, categories, units, data types and flags at startup and once after warmup; this refresh can perturb the transition frame. Exact ambiguous/missing/unsupported identities produce unbound samples. GPU markers are not installed. Selected time markers use `SumAllSamplesInFrame`; other selected metrics retain their raw publication values. The collector is limited to integer metric data types.

`cpu-thread-samples.csv` retains caller Stopwatch timestamp, read brackets, observed Unity frame/pose, OS thread ID, cumulative kernel/user counters, validity and Win32 errors. The [Windows GetThreadTimes contract](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getthreadtimes) defines kernel/user CPU service amounts in 100ns units. Those units do not establish effective sampling resolution. Differences give CPU service between polls; wall minus CPU combines blocked, ready/preempted and other unclassified time. This collector supplies no stacks or scheduling timeline.

`cpu-marker-samples.csv` retains configured marker ordinal, poll timestamp/frame/pose, native publication count, raw LastValue and read state. State 0 means unbound/unsupported/ambiguous, 1 means no publication, 2 means publication count stayed stable across the read, 3 means a concurrent publication, and 4 means exhausted capacity. State 2 does not establish a new publication. Held values must not be summed repeatedly, and poll Unity frame is not a source frame. Marker aggregates can include multiple threads and nested scopes. Units other than TimeNanoseconds are not converted to milliseconds. The [Unity 6000.6 API](https://docs.unity.com/en-us/engine/6000.6/script-reference/unity/profiling/profilerrecorder) supports Release Players while availability is established by GetAvailable.

`cpu-marker-config.json` retains the actual requested configuration. `release-cpu-diagnostic.json` records bounds, errors, disposal failures, thread identity, Stopwatch frequency and start/end native-QPC brackets plus UTC anchors. The brackets use the same static Mono Stopwatch source as the route timestamps; equal frequencies do not imply equal epochs. No per-frame QPC or file I/O is installed. Managed sample storage and each recorder have fixed 32768 capacity, without ring overwrite; overflow invalidates the session. Read and recording overhead belongs to the diagnostic and must be assessed with separate matching controls. CPU/GPU/marker/thread durations are not added into an exclusive frame budget.

## Native submission experiment

`-instance-native-submission A|B` is an independent opt-in benchmark-session override. A selects the original legacy path. Current B requests BRG `Camera` color and `Light` shadow submission; once native preparation succeeds, the complete legacy instance loop is skipped. The original path remains the fallback for unsupported data, materials, moving/exposed matrices, LOD/distance/grouping requirements or unsupported camera contexts. The override preserves each renderer's prior nullable value and restores it on completion, Abort and exit without saving GameConfig assets. `run_benchmark.py --native-submission A|B` passes the option; keep grouping U for the current comparison. Production GameConfig enables native submission by default and keeps grouping disabled. Removing this module preserves these defaults. The flag alone establishes neither image equivalence nor a performance gain.

Native shadow culling requires the functional HDRP `HDShadowCullingCameraScope` API with `ApiVersion=1` and the expected getter signatures. Missing or incompatible ownership API prevents native preparation and uses the original path. A Light callback contributes commands only when its scope owner matches the prepared Game camera and its layer mask includes the renderer. Color, Light and reflection candidates are independent. This campaign's owner scope is the Game camera and reflection coverage must be established from actual view and command evidence or dedicated visual fixtures. Registered reflection support and counters remain separate, while unsupported contexts retain the original fallback.

`native-submission-mode.json` records the requested override, build GUID and source counts at startup. `native-submission-after.json` observes published use before restoration; `active` describes the current context and may be false after EndContext. Technical runs record emitted Camera and Light commands, repeated instance references, accepted views, culling invocations, output storage and per-renderer fallback reasons. Shadow commands are source/submesh commands per accepted Light view; the same source instances can repeat across submeshes, lights and views. These counters are not GPU draw calls, unique visible objects or exclusive pass costs. Zero shadow commands can reflect no eligible shadow work or unobserved coverage; verify actual view/caster coverage separately.

`submissions/submittedInstances` count legacy `Graphics.RenderMeshInstanced` API invocations and argument references. Zero in successful B means zero calls through that API; BRG still produces geometry and shadow work. Positive B values indicate fallback or another retained legacy path and require their own attribution. `colorInstances` describes legacy color submission and may be zero in B. Compare geometric `colorCandidateInstances` independently from native camera instances; candidate counts do not include native rejection or visible pixels.

The BRG global registration bound encloses separate physical source bounds, authored bounds and transformed mesh corners, including applicable wind expansion. Prepared source/index bounds serve spatial candidate selection and remain a distinct data contract. A physical global bound is not a count of visible/index candidates, and a missing Light callback is not evidence that index traversal rejected every source. Preserve conservative registration coverage without silently changing index eligibility.

The technical renderer wrapper measures Game and Reflection preparation separately. Successful native B omits the full legacy source traversal and legacy shadow submission; preparation still excludes later native culling. Only `-batching-counters` installs `BenchmarkNativeCullingObserver` after group creation. It forwards the installed Unity version's original synchronous `OnPerformCulling` delegate for observed Camera, Light and registered reflection views, preserving arguments, JobHandle and exceptions. It restores the callback before session overrides are released on Abort/completion/disable/exit. Count/sum/mean/max retain their actual callback populations; no publication is assigned a source Unity frame from its poll time.

Historical retained Players that used BRG color with legacy `ShadowsOnly` still describe that earlier hybrid. Their saved metadata and measurements are unchanged. They do not establish the behavior or timings of current Camera+Light B.

Combined observed synchronous elapsed work is `(cpuMicrosecondsSum + reflectionCpuMicrosecondsSum + nativeCullingElapsedMicrosecondsSum) / cpuSamples`, with separate Game, Reflection and native-view sample counts. Do not add means from these different populations. Missing timing keeps the combined result unavailable. Label it per-frame only when one renderer and one Game camera are established; otherwise it is per observed Game renderer callback. Begin/EndContext callbacks, downstream native work, later asynchronous jobs and GPU execution are excluded. The elapsed sums are not exclusive CPU execution time or a complete sequential frame budget.

Native timing is usable only when `nativeCullingTimingAvailable` is true. Missing metadata, absent groups/samples, changed callbacks and capacity overflow retain an explicit unavailable reason; numeric defaults with unavailable status are not a zero-cost result. Callback restoration status is written to `native-culling-observer-restoration.json`; active restoration failures invalidate teardown rather than silently leaving a wrapper installed. Each technical pose separately snapshots process private bytes and working set through the current Process, and approximate managed heap through GC.GetTotalMemory(false), without forcing collection. These are instantaneous memory scopes, not per-frame allocation counts. Native storage estimates, per-view output allocation totals, Unity Profiler total allocated memory, process memory and managed heap overlap and must not be added. Compare each route/position separately; one technical A/B snapshot pair does not establish a stable memory regression or zero allocation. Main timing runs take none of these memory snapshots.
